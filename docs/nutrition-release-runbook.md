# Є ПЛАН — перенесення конструктора харчування (PR #88)

**Статус:** staging candidate. Не зливати у `main` і не розгортати production без нижчезазначених перевірок.

## Межі інтеграції

- Основою є актуальна `main` (включно з optional RIR v298); інтеграційна гілка: `integration/nutrition-real-v1-20261012`.
- Тренер: вкладки цілих раціонів, 60 перевірених коротких рецептів (15 для кожної категорії), заміна страви, автоматичне підлаштування порцій за залишком БЖВ, явне підтвердження призначення.
- Клієнт: вкладки повних раціонів, без можливості змінювати продукти; для старих неповних альтернатив збережений попередній вигляд.
- Харчова база: тільки схвалені source_id; довільні БЖВ із браузера сервер не приймає.
- Схема: адитивне `nutrition_plan_items.foods_json TEXT NOT NULL DEFAULT '[]'` із `IF NOT EXISTS`; старі текстові записи не переписуються під час міграції.
- Збереження — лише дія тренера, попередній план **не видаляється** до валідації всіх надісланих продуктів.

## Вже автоматично перевіряється

GitHub Actions `release-gate.yml` для PR: Python/JS syntax, контракти, браузерні тести фактичного UI, авторизовані food API, PostgreSQL 16 міграція зі старої таблиці + save/reload + відхилення некоректного source_id, повторний init, PostgreSQL 18 RIR regression, dependency audit.

## Connected staging QA — обов'язковий блокер

На Render є окремі `e-plan-staging` та `my-diary-db-staging`. Сервіс staging зараз прив'язаний до `redesign-v1`, **не до цієї інтеграційної гілки**. База staging правильно забороняє зовнішнє підключення; **не послаблювати IP allowlist**.

1. Підняти тестовий веб-сервіс з **цієї інтеграційної гілки** у внутрішній мережі Render і приєднати **тільки** `my-diary-db-staging`, ніколи production `my-diary-db`. До створення нового платного ресурсу узгодити витрати.
2. Перевірити відсутність production секретів/ідентифікаторів у staging; підготувати окремого тестового тренера і клієнта.
3. У staging виконати міграцію, двічі перезапустити застосунок і переконатися, що стара текстова програма харчування незмінна.
4. У тренері створити 2+ повних раціони, замінити сніданок/обід із каталогу, перевірити підібрані грамовки та різницю до цілі; яйця — цілі штуки, олія — компонент страви, овочі враховуються у фактичних БЖВ.
5. Зберегти, оновити сторінку, повторно відкрити клієнта і перевірити всі продукти, вагу, опис приготування та окремі раціони.
6. Перевірити клієнтський перегляд: вкладки `Раціон 1/2`, не сумувати альтернативи, read-only для клієнта, заморожений доступ і тариф без харчування.
7. Перевірити старий план із частковими альтернативами та клієнта без призначеного плану.
8. Перевірити iPhone Safari/PWA після оновлення кешу, Android Chrome, браузер desktop, офлайн-повернення, відсутність чорного екрана.
9. Перевірити помилки save/reload, відключення мережі, подвійний клік, довгий опис страви та некоректний source_id — попередній план повинен залишатися на місці.
10. Зібрати скриншоти та підтвердження тестів до остаточного дозволу на release.

## Rollout / rollback

- Перед релізом: знімок production PostgreSQL або підтверджений відновлюваний backup, зафіксований SHA чинної `main`, позитивний staging QA.
- Реліз: merge PR #88 **тільки після** staging і ручного підтвердження; перевірити Render deploy, `/health`/boot, PWA, trainer/client, збереження тестового раціону.
- При проблемах: повернути попередній **app commit/deploy**; не видаляти `foods_json` і не робити масового rollback схеми. Дотриматися резервної копії перед ручним поверненням даних.
- Важливо: старий код не знає про `foods_json`; повторне редагування раціонів у старій версії може втратити структуровані поля. Після відкату тимчасово заборонити зміну планів харчування до виправлення.

Жодна автоматична перевірка не замінює реального connected staging QA на Render.
